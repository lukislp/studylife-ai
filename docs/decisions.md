# Design Decisions

Log of notable decisions: what was decided, alternatives considered, and why. Marked as **[owner: assistant]** for boilerplate/infra calls made per CLAUDE.md, or **[owner: user]** for calls in the assist-only areas (chunking, retrieval, prompts, agent loop, eval design, security design).

## M1 — Repository scaffold

### 2026-08-10 — Package manager: uv **[owner: assistant]**
- **Decision:** Use `uv` with a standard PEP 621 `pyproject.toml` for dependency management, instead of Poetry or plain pip/venv.
- **Alternatives:** Poetry (mature, but its own lockfile format and slower); plain pip + requirements.txt (no lockfile, weaker reproducibility).
- **Why:** Already installed locally, fast, and works with standard `pyproject.toml` rather than a tool-specific format — lower lock-in.

### 2026-08-10 — src-layout **[owner: assistant]**
- **Decision:** Application code lives under `src/studylife_ai/`, not a flat top-level package.
- **Why:** Standard practice for installable Python packages; prevents accidentally importing the working-tree copy instead of the installed package during tests.

### 2026-08-10 — SSE without `sse-starlette` **[owner: assistant]**
- **Decision:** Implement Server-Sent Events manually via Starlette's `StreamingResponse` and hand-formatted `data: ...\n\n` lines, instead of adding the `sse-starlette` dependency.
- **Why:** The format needed (OpenAI-style `data: {json}` + `data: [DONE]`) is a few lines; adding a dependency for it isn't justified yet. Revisit if SSE needs (retry hints, event IDs, per-connection heartbeats) grow.

### 2026-08-10 — Default LLM model: local Ollama **[owner: assistant]**
- **Decision:** `LLM_MODEL` defaults to `ollama/llama3.1`, `LLM_API_BASE` to `http://localhost:11434`.
- **Why:** Lets `docker compose up` produce a working `/chat` endpoint with zero API keys. Provider-specific keys (e.g. `OPENAI_API_KEY`) are intentionally *not* modeled in `Settings` — LiteLLM reads them directly from the environment based on the `LLM_MODEL` prefix, avoiding a second source of truth for credentials.

### 2026-08-10 — docker-compose includes Qdrant + Ollama from M1 **[owner: assistant]**
- **Decision:** `docker-compose.yml` starts `qdrant` and `ollama` services already, even though the app doesn't use Qdrant until M2.
- **Why:** Per CLAUDE.md, the full local dev compose (service + Qdrant + Ollama) is boilerplate owned end-to-end; starting it now means M2 doesn't need an infra change, just application code.

### 2026-08-10 — StudyLife API integration deferred **[owner: user via CLAUDE.md]**
- **Decision:** No StudyLife REST API client built in M1; API base URL, auth scheme (bearer token vs. API key), and relevant endpoints (notes, sessions, calendar) are still unknown to this assistant.
- **Why:** M1's `/chat` endpoint doesn't call the StudyLife API — only LiteLLM. Needed for M2 (ingestion reads from the StudyLife DB directly, not the API) and concretely for M4 (agent tools call the StudyLife REST API). Will ask for OpenAPI spec / endpoint details / auth scheme when M4 starts, per CLAUDE.md instruction not to assume.

## M2 — Ingestion architecture (planning, ahead of implementation)

### 2026-08-10 — Ingestion reads via the StudyLife REST API, not direct DB access **[owner: user]**
- **Decision:** The M2 ingestion worker will call the StudyLife REST API to pull notes/courses/calendar data, rather than reading the StudyLife database directly as originally specified in CLAUDE.md's architecture table ("Ingestion: Python-Worker, liest Notizen aus der StudyLife-DB").
- **Alternatives:** Direct DB access (original CLAUDE.md spec) — faster, no extra HTTP hop, but couples `studylife-ai` to StudyLife's internal schema and bypasses its access-control logic; breaks silently on StudyLife schema migrations.
- **Why:** Decoupling from the internal schema and reusing StudyLife's existing access logic/auth outweighs the minor performance cost of going through the API. This overrides the CLAUDE.md architecture table — flagged as a deliberate architecture change, not a silent one.
- **Status:** CLAUDE.md's architecture table updated same day to reflect this (no longer says "liest Notizen aus der StudyLife-DB"). API shape confirmed by reading the StudyLife source directly:
  - `GET /api/notes` (`NotesController.cs`) returns all notes, no pagination.
  - Auth is a custom `X-Api-Key` header/middleware (not JWT/Identity) — built explicitly for non-interactive integrations (the code comments cite the existing Home Assistant integration as the reference use case); minted once via the StudyLife UI after a passkey login, then usable indefinitely as a static credential. No tenant-less service account exists — the key is bound to one StudyLife user.
  - No Swagger/OpenAPI in the StudyLife repo; `StudyLife.Shared/Dtos.cs` is the closest thing to a spec.

### 2026-08-11 — Incremental sync: client-side full-list diff (Option A), not a StudyLife API change **[owner: user]**
- **Decision:** The M2 ingestion worker polls `GET /api/notes` for the full list on every sync and diffs it client-side against the last known state, rather than having StudyLife's API do server-side filtering.
- **Mechanics:** Each Qdrant point carries `note_id` (+ a change fingerprint — `updated_at` or a content hash, still to be decided when the ingestion pipeline is actually built) as payload metadata; Qdrant itself is the "last known state" — no separate manifest/state store. Per sync: note ID present now but not before → new (chunk + embed + upsert); ID present both times with a changed fingerprint → changed (delete its existing chunks, re-chunk + upsert); ID known before but missing now → deleted (delete its chunks). Requires being able to filter-delete Qdrant points by `note_id` payload.
- **Alternatives:** Add an `updatedSince` query param to `NotesController.GetAll` (+ soft-delete/tombstone support for detecting deletions) so the ingestion worker only transfers what changed. More bandwidth-efficient, but requires changing and redeploying the separate StudyLife repo, including a data-model change (hard→soft delete) for deletion detection to work at all.
- **Why:** At this project's scale (one user's personal notes, likely low-thousands at most), the full-list transfer per sync is negligible (single-digit KB) — the bandwidth savings of the alternative don't justify touching a different, already-running production repo and its own release cycle. Ships entirely within `studylife-ai`, independent of StudyLife's deployment schedule.
- **Backlog — revisit later:** If note volume or sync frequency ever make the full-list transfer a real cost, revisit adding `updatedSince` to `NotesController.GetAll` on the StudyLife side to cut bandwidth. Not blocking for M2; noted here so it isn't forgotten.
- Same underlying question (no `UpdatedAt` on `StudySessionDto` at all) applies to `api/sessions` if session data ends up in ingestion scope — same client-side-diff approach would apply, just with content-hash as the only viable fingerprint since there's no timestamp to compare.

### 2026-08-11 — Chunking strategy: fixed-size with overlap, sentence-aligned **[owner: user]**
- **Decision:** Chunk note content into ~500-token windows with ~15% (≈75 token) overlap, boundary snapped to the nearest sentence break. Size measured via `tiktoken` (already a transitive dependency via LiteLLM/OpenAI) as an approximation, independent of the actual embedding model used.
- **Alternatives considered:** (1) whole-note-as-one-chunk — simplest, unambiguous source attribution, but embeddings dilute on long notes and can exceed embedding context limits; (3) paragraph-based split with size fallback — better semantic coherence, more implementation complexity/edge cases; (4) hybrid of 1+3 by a length threshold — best long-term fit, but the right threshold can't be picked without real usage data on how long/structured the user's actual notes are.
- **Context that ruled out a structure-aware split**: checked `Notes.razor:173` in the StudyLife source — note content is edited via a plain `<textarea>`, no Markdown/rich-text editor, no enforced structure, no length limit. So "Struktur-Awareness" (as named in CLAUDE.md) can't mean Markdown-header-based splitting; there's no reliable syntax to split on.
- **Why fixed-size over the others for the M2 starting point:** industry-standard default, works regardless of whether a given note happens to have paragraph structure or not, and the Qdrant payload schema (`note_id`, `chunk_index`, `title`, `course_id?`, `session_id?`, fingerprint) doesn't need to change if we later move to paragraph-based or hybrid chunking — so this isn't a dead end, just a simple starting point. Revisit once RAGAS eval (M3) shows whether chunk quality is actually a problem.
- Each Qdrant point's payload also needs `note_id` for the delete-on-change/delete-on-removal mechanics from the sync-strategy decision above.

### 2026-08-11 — Single-user scope for now; multi-user kept option-open in the data model **[owner: user]**
- **Decision:** `studylife-ai` targets a single StudyLife user for now (one `X-Api-Key` in config) — no per-request auth, no user routing in the `/chat` endpoint. Qdrant chunk payload still gets a `user_id` field (populated from config/the API key's owning account), even though nothing filters on it yet.
- **Why single-user now:** A StudyLife API key is bound to exactly one `AuthUserId` and only ever returns that user's data — so with one key configured, there's no cross-user data risk to design against yet. Building multi-user routing (which of possibly several StudyLife accounts is "the current chat user", managing multiple API keys, mandatory retrieval-time `user_id` filtering) pulls in scope that belongs with M4 (agent/API auth), not M2 ingestion.
- **Why keep `user_id` in the payload anyway:** StudyLife itself is multi-user (family members, fully separated data) — if `studylife-ai` ever needs to serve more than one StudyLife account, retrofitting `user_id` after the fact means re-ingesting every note. Adding the field now costs nothing (single constant value today) and avoids that migration later.
- **Backlog — revisit later:** Multi-user support (auth in the FastAPI service to know "who's asking", per-account API key management, mandatory `user_id` filter at retrieval time so one family member's queries can never surface another's notes/grades) is deferred, not designed yet. Flagging explicitly so it isn't silently forgotten, given StudyLife's own multi-user design makes this a plausible future need, not a hypothetical one.

### 2026-08-11 — Dedicated StudyLife API key for studylife-ai, not the shared Home Assistant key **[owner: user]**
- **Decision:** StudyLife got a second, independent API key slot (`AuthUserEntity.AiApiKeyHash`, endpoints under `api/settings/ai-api-key`) specifically for `studylife-ai`, instead of reusing the existing Home Assistant key (`ApiKeyHash`, `api/settings/ha-api-key`). Implemented as a full mirror of the HA key feature: entity field + EF migration (SQLite + Postgres), controller endpoints, a setup-page card, i18n in all 26 languages, tests — in the StudyLife repo, not this one.
- **Alternatives:** Reuse the Home Assistant key value for studylife-ai too — zero cross-repo work, but the two integrations would share one credential: leaking or rotating it breaks/endangers both, with no independent revocation and no separate audit trail.
- **Why:** StudyLife's `ha-api-key` mechanism is a single slot per user with no separate service-account concept — sharing it across two unrelated integrations is a real blast-radius/credential-hygiene issue, not just untidy. Mirroring the existing pattern (rather than generalizing into a named multi-key system) matches StudyLife's own CLAUDE.md stance against premature abstraction — there are exactly two integrations today.
- **Where the change lives:** entirely in the `studylife` repo (commit `f9b856a`), not `studylife-ai`. `studylife-ai`'s only change is that `.env`'s `STUDYLIFE_API_KEY` now comes from the "studylife-ai connection" setup card, not the Home Assistant one.

### 2026-08-11 — Retrieval design v1: fixed top-k, pure vector search, no reranking, `user_id`-only filter **[owner: user]**
- **Decision:** All four retrieval sub-questions from CLAUDE.md resolved the same way for v1 — the simplest option everywhere:
  - **Top-k**: fixed (`RETRIEVAL_TOP_K`, default 5), not a similarity-threshold cutoff.
  - **Hybrid search**: pure dense vector search only, no sparse/BM25 component.
  - **Reranking**: none — top-k from the vector search is the final context, no cross-encoder second pass.
  - **Metadata filter**: `user_id` only (already required by the single-user/multi-user-ready decision above); no `course_id`/`session_id` filtering yet.
- **Alternatives considered:** similarity-threshold top-k (hard to tune without data); hybrid dense+sparse via Qdrant's native sparse vectors (real recall improvement for keyword-heavy queries, but a new encoder dependency and cost at both ingestion and query time); cross-encoder reranking (more precise, but a new model + per-query latency); LLM-inferred or UI-driven metadata filters (powerful/precise respectively, but the former is error-prone and the latter needs the not-yet-built Blazor chat UI).
- **Why:** No evaluation data exists yet to justify the added complexity/latency/dependencies of hybrid search, reranking, or smart filtering. M3 (RAGAS, explicitly including "Context Precision") will give real evidence of whether retrieval quality is actually a problem and where — better to establish a simple baseline first and add specific complexity only where measurement shows it's needed, rather than guessing upfront. None of these four choices lock in future retrieval architecture — the Qdrant payload schema doesn't need to change to add hybrid/reranking/filters later.
- **Scope boundary noted:** this decision covers *which* chunks get retrieved, not *how* they're formatted into the LLM prompt (citation format etc.) — that's the separate, not-yet-discussed "Prompt-Design für RAG-Antworten" decision. The retrieval module is therefore built standalone (embed query → Qdrant search → structured results) and not yet wired into `/chat`.

### 2026-08-11 — Prompt design v1: dedicated context message, inline+deterministic citations, honest-then-helpful fallback **[owner: user]**
- **Decision**, resolving all five prompt-design sub-questions:
  - **Context placement**: retrieved chunks go into their own system message (not inlined into the user's question).
  - **Citations**: hybrid — the model is instructed to cite inline with `[n]`, but the SSE stream *always* appends a deterministic `sources` event built from the actual retrieved chunks afterwards, regardless of whether the model cited correctly (or at all). Best case: precise inline attribution. Worst case: still a correct source list.
  - **Data/instruction boundary**: retrieved note content is wrapped in explicit `<notes>...</notes>` markers with an explicit instruction that content inside is data, not commands to follow — the prompt-injection boundary named in CLAUDE.md's security-design list, applied now so the same pattern is ready for M4's tool outputs.
  - **When retrieval fires**: on every `/chat` call, using the latest user message as the query — no opt-in flag yet.
  - **Empty/irrelevant retrieval**: hybrid — the model must say honestly that nothing relevant was found in the notes *first*, then may still attempt a general-knowledge answer, clearly marked as not sourced from the notes (refined from a pure "refuse" behavior during discussion).
- **Alternatives considered:** inlining context into the user message (simpler, worse separation); deterministic-only citations (robust but imprecise — only says "these notes were in context," not what was actually used); structured JSON output with `answer`+`sources` fields (most precise, but breaks the plain-text SSE streaming M1 already ships); an opt-in retrieval flag or LLM-decided retrieval (both deferred — the latter is really M4 agent-loop territory); a pure refuse-if-empty behavior (rejected as too rigid for a study assistant that should still be generally useful).
- **Why:** Each choice is the version that's most useful without locking in complexity the project doesn't have evidence for yet (same reasoning as the retrieval-design decision) — e.g. structured output would be more precise but conflicts with an already-shipped design choice (SSE text streaming) for a precision gain that's speculative before RAGAS data exists.
- **SSE protocol change**: a new event `{"sources": [{"note_id", "title", "course_id"}, ...]}` is emitted once, always (both on success and on an LLM streaming failure), right before `data: [DONE]` — deduplicated by `note_id` even if multiple chunks of the same note were retrieved. `[n]` citation numbers in the prompt and `sources` array order are guaranteed aligned (grouped by note, not by raw chunk). Documented in the `/chat` API description.
- **Follow-up from code review (same day)**: the initial implementation had the `<notes>` boundary actually breakable — a note whose own content happened to contain the literal string `</notes>` could close the data block early and have its own trailing text read as instructions, defeating the boundary this decision exists to create. Fixed by HTML-entity-escaping `<`/`>` in note title/content before insertion. Also fixed: `sources_payload` returned raw dicts instead of a Pydantic model (`NoteSource`, added to `schemas/chat.py`), per CLAUDE.md's "Pydantic-Modelle für alle API-Schemas" rule; the `sources` event was only emitted on the success path, so a mid-stream LLM failure silently dropped it — moved outside the streaming try/except so it's always sent.

### 2026-08-11 — Scope check: M2 covers notes only, not courses/calendar **[owner: user]**
- **Decision:** Confirmed (not assumed) that the current pipeline only ingests `GET /api/notes` — `api/courses` and `api/sessions` are never called. Note chunks carry `course_id`/`session_id` as plain reference numbers from `NoteDto`, not actual retrievable course/calendar content (no course names, topics, or calendar entries in the index). The README's "notes, courses, and calendar data" line is the M1 project vision (explicitly future-tense, "It will provide"), not a claim about M2's actual scope — flagged because it's easy to misread as already done.
- **Backlog — added to README roadmap**: ingest courses and calendar/session data too, so RAG reaches full "notes, courses, calendar" coverage. Expected to extend the existing M2 pieces (StudyLife client gets `get_courses()`/`get_sessions()`, chunking/embedding/retrieval are already generic over content, not notes-specific) rather than needing a redesign — not yet scheduled to a specific milestone.
- **Why this matters for M3:** the RAGAS eval set must only contain questions the system can actually answer today (notes-based) — course/calendar questions would fail for a reason that has nothing to do with retrieval/prompt quality, and would corrupt the baseline metrics.

### 2026-08-11 — M3 eval design: hybrid testset, independent judge model, no CI thresholds yet **[owner: user]**
- **Decision**, resolving the M3 eval-design sub-questions (metrics themselves — Faithfulness, Answer Relevancy, Context Precision — were already fixed by CLAUDE.md, not re-decided here):
  - **Testset construction**: hybrid — assistant drafts questions/notes, user reviews before anything is built. First step of this: expanded the dev corpus from 3 to 10 notes (7 added via the StudyLife API against the local dev instance, not through StudyLife's own DemoSeeder — no StudyLife-repo change needed), spanning both same-course pairs (tests whether retrieval discriminates between similar-topic notes, e.g. two Lineare-Algebra notes) and unrelated courses (tests it doesn't cross-contaminate), plus one course (Cloud Computing) deliberately left without any note, as the "nothing relevant found" test case.
  - **Judge model**: a separate, stronger model than the answer-generation model (not the same model judging itself) — RAGAS' own recommendation, needed for trustworthy scores. Specific provider deferred (see below).
  - **CI trigger**: eval job on every push to `main` once wired in, not on every PR commit — keeps a paid judge's cost bounded. No CI score thresholds yet; the first real run establishes the baseline, thresholds are a follow-up decision once real numbers exist (inventing them now would violate CLAUDE.md's no-fabricated-metrics rule).
- **Deferred, explicitly not decided yet**: which API provider the judge model uses (OpenAI/Anthropic/other) and the resulting `OPENAI_API_KEY`-style GitHub Actions secret + real per-run cost. User chose to build and validate the eval pipeline locally first, decide the provider/secret afterwards — not blocking pipeline construction on a procurement decision.
- **Why**: Same reasoning pattern as M2's decisions — sequence "build and validate the mechanism" before "commit to the expensive/hard-to-reverse part" (here: a paid API key as a standing CI cost) wherever the two can be separated.

### 2026-08-11 — Judge model resolved: `openai/gpt-4o-mini` **[owner: user]**
- **Decision**: resolves the "deferred" item above. Judge provider is OpenAI, model `gpt-4o-mini`, set via `EVAL_JUDGE_MODEL` (local `.env` for now; GitHub Actions secret still pending, needed once the eval job is wired into CI).
- **Alternatives considered**: `gpt-4o` — stronger, potentially more reliable judgments on subtle faithfulness cases, but noticeably more expensive per eval run.
- **Why**: `gpt-4o-mini` is far cheaper (~1/20 the cost of `gpt-4o`) and sufficient for scoring a 12-case testset; keeps a portfolio project's standing eval cost low. Can be revisited if scores look unreliable once real numbers exist.

### 2026-08-11 — Context Precision implementation: `LLMContextPrecisionWithoutReference` **[owner: assistant]**
- **Follow-up from code review**: ragas 0.3.9 ships two concrete classes for the "Context Precision" metric CLAUDE.md names — `ContextPrecision` (= `LLMContextPrecisionWithReference`, needs a ground-truth reference answer per question) and `LLMContextPrecisionWithoutReference` (judges precision from the generated response itself). The eval set intentionally has no reference answers (only `expected_note_titles`, used separately by the non-LLM note-match check), so `ContextPrecision` would fail every run with a missing-column error. Switched to the reference-free variant, which needs only `user_input`/`response`/`retrieved_contexts` — fields the pipeline already produces. Not a metric-selection decision (that stayed as CLAUDE.md specified), just which concrete implementation of it fits data we actually have.

### 2026-08-11 — First real eval run: baseline established, `answer_relevancy` re-run pending **[owner: assistant]**
- **What happened**: first live run of `python -m studylife_ai.eval` against the real dev Qdrant/StudyLife data, judged by `openai/gpt-4o-mini`. Note-match rate 92% (11/12 — the one miss, `statistik-breit`, is a broad cross-note question retrieval doesn't fully cover at `top_k=5`, a real retrieval-design data point, not an eval-pipeline bug). Faithfulness 0.82, Context Precision 0.50. `answer_relevancy` came back `NaN` for every case: partway through the run, the OpenAI account (new, low-tier) hit its daily request-rate limit (`RPD: Limit 10000, Used 10000`) — `AnswerRelevancy` alone issues several LLM calls per case (generates candidate questions, embeds them), so it exhausted the shared judge-call budget before the other two metrics did. Not a bug in our code; documented here per CLAUDE.md's "no fabricated metrics" rule rather than inventing a number. Also tried running answer generation concurrently across eval cases (`asyncio.gather`) to speed up local iteration — reverted immediately: local Ollama serializes requests internally, so concurrent calls queue up and blow the 60s per-call timeout instead of actually running in parallel. Sequential is correct for the current single-Ollama-instance setup.
- **Also decided**: switched the local `LLM_MODEL` (answer generation, not just the judge) from `ollama/llama3.2` to `openai/gpt-4o-mini` for this environment going forward — faster and avoids local timeouts during iteration. `.env.example`/README still document Ollama as the zero-key default for others; this is a personal `.env` override, not a change to the documented default.
- **Correction (see next entry)**: the `answer_relevancy` `NaN` here was initially blamed solely on the OpenAI rate limit. That was incomplete — a real code bug (wrong embeddings wrapper) was the actual cause and would have broken every run, rate limit or not.

### 2026-08-11 — CI eval job: committed fixture corpus, seeded fresh each run **[owner: user]**
- **Decision**: CI has no access to the real local StudyLife dev instance (local-machine only) and no local Ollama, so the eval job needs a self-contained substitute for both. Chose to commit a small fixed note corpus ([`eval/fixture_notes.jsonl`](../eval/fixture_notes.jsonl) — the same 10 notes used to build and locally validate `eval/dataset.jsonl`), seeded into a throwaway Qdrant service container at the start of the job (`src/studylife_ai/eval/fixture.py` + `seed_fixture.py`), rather than deferring CI wiring until a "real" data source exists.
- **Alternative considered**: wire the job now but trigger it manually only (`workflow_dispatch`) instead of automatically on push to main, postponing the fixture-corpus question. Rejected in favor of building the fixture now — not meaningfully harder, and matches the original "every push to main" decision instead of weakening it.
- **Consequence**: CI's `LLM_MODEL` and `EMBEDDING_MODEL` are also switched to OpenAI for this job (no Ollama in CI) — meaning every push to main now costs a small amount on the same `OPENAI_API_KEY` used for judging, on top of the judge calls. Kept to `gpt-4o-mini` / `text-embedding-3-small` for the same cost reasons as the judge-model decision above.
- **Still open**: first live CI run is unverified — local dry-runs against the real OpenAI API hit account-level rate limits (first a 10,000 RPD org-wide limit, then a much stricter 50-request limit that didn't match the account's stated Tier-1 page; likely a separate, lower per-project rate limit — needs checking in the OpenAI dashboard under project-level Limits, not the org Tier overview). The fixture-seeding step itself was verified end-to-end locally.

### 2026-08-11 — Two real CI bugs found via the first live GitHub Actions run **[owner: assistant]**
- **Bug 1 — `LLM_API_BASE` not cleared for the eval job**: `Settings.llm_api_base` defaults to Ollama's URL (`http://localhost:11434`) for local dev. The CI job's env block set `LLM_MODEL`/`EMBEDDING_MODEL` to OpenAI models but never cleared `LLM_API_BASE`, so `stream_chat_completion` forced even the OpenAI answer model through that unreachable local address - every case failed with `ConnectionRefusedError`. Fixed by explicitly setting `LLM_API_BASE: ""` in the job's env (mirrors the same fix already needed in the local `.env` when switching `LLM_MODEL` to an API provider).
- **Bug 2 — wrong embeddings wrapper for the judge**: with `LLM_API_BASE` fixed, the next CI run surfaced `AttributeError: 'LiteLLMEmbeddings' object has no attribute 'embed_query'` from `AnswerRelevancy` (a legacy ragas metric). Same root cause as the `llm_factory()` vs `BaseRagasLLM` mismatch found earlier: `ragas.embeddings.litellm_provider.LiteLLMEmbeddings` implements ragas' newer `embed_text`/`embed_texts` interface, not the legacy `BaseRagasEmbeddings` interface (`embed_query`/`embed_documents`) the metric actually calls - confirmed via `issubclass()`, same as before. Fixed by writing a small custom `_JudgeEmbeddings(BaseRagasEmbeddings)` adapter in `runner.py` that calls `litellm.embedding`/`litellm.aembedding` directly and implements the four methods the legacy interface requires - verified end-to-end against the real OpenAI embeddings API before integrating.
- **Also found while fixing this**: `LangchainLLMWrapper`'s `n=` parameter (requests multiple generations per call for Faithfulness' statement-generation robustness) silently returned only 1 generation instead of 3 via `ChatLiteLLM`. Fixed with `bypass_n=True`, which makes ragas issue `n` separate calls instead of relying on the provider returning `n` completions in one call.
- **Result**: a fully clean run (no errors, no `NaN`) against both the CI fixture corpus and the real dev corpus. README's Evaluation baseline table now reflects the real dev-corpus numbers: Faithfulness 0.80, Answer Relevancy 0.88, Context Precision 0.58, note-match 92% (same single miss as before - a real retrieval-design data point, not a bug).

### 2026-08-11 — Reverted `bypass_n=True`: reliable degraded score beats a reliably-NaN one **[owner: assistant]**
- **What happened**: the actual CI run (not just a local dry-run) showed `bypass_n=True` was a net loss. 26 of 36 judge sub-calls timed out (`RunConfig`'s default 180s), almost all on `faithfulness` - the metric with by far the most LLM calls per case (statement generation, tripled by `bypass_n`, plus a per-statement verdict call), leaving its score fully `NaN`. Locally this didn't show up, since GitHub Actions runners apparently have higher/more variable latency to OpenAI than this dev machine.

With no CI thresholds depending on the exact value yet, reliability wins.
- **Updated baseline** (same dev corpus, same day, after reverting): Faithfulness 0.77 (was 0.80 with the since-reverted `bypass_n=True` run), Answer Relevancy 0.90, Context Precision 0.58, note-match still 92%. The small faithfulness delta is exactly the n=1-vs-n=3 sampling difference this decision accepts.
- **Still open**: if CI timeouts recur even without `bypass_n`, the next lever is `RunConfig` (raise `timeout`, lower `max_workers` from its default 16 to reduce concurrent-call contention) - not applied yet since reverting `bypass_n` alone was enough to fix it locally.

### 2026-08-11 — CI eval job confirmed working end-to-end **[owner: assistant]**
- **What happened**: a follow-up CI run (still without `bypass_n`) again timed out entirely on `faithfulness`, confirming the default `RunConfig` (16 concurrent judge calls, 180s timeout) was too aggressive for GitHub Actions' network path to OpenAI on its own. Passed `run_config=RunConfig(timeout=300, max_workers=4)` to `evaluate()` - trading wall-clock time for reliability, since this job doesn't need to be fast.
- **Result**: next CI run had exactly one isolated timeout (down from 26, then 7) and still finished with a fully clean result - faithfulness 0.83, answer relevancy 0.88, context precision 1.00, note-match 100% (against the fixture corpus). CI eval job is now considered working; M3 is done.
- **Considered and rejected**: switching the judge model up to `gpt-4o` to reduce timeouts. Larger models are typically slower to respond, not faster, so this would likely worsen timeout risk while also multiplying cost - rejected without needing to test it.

## Ingestion scope expansion: courses, sessions, course goals

### 2026-08-11 — Ingestion scope expansion: what, how much history, storage, templates **[owner: user]**
- **Decision**, closing the "M2 covers notes only" gap noted above, now that M3 is done:
  - **Scope**: ingest Courses, Sessions, and CourseGoals from the StudyLife API (not CourseResources or SessionTemplates - lower RAG value, link-only content).
  - **Session window**: `GET /api/sessions/history?days=1825&onlyCompleted=false` - ~5 years back, both planned and completed sessions. `GET /api/sessions` (the other session endpoint) is hard-capped to a fixed -7d/+90d window and unusable for ingestion.
  - **Storage**: one Qdrant collection for all content types (not separate collections per type), disambiguated by a new `content_type` payload field - keeps retrieval a single search call across everything.
  - **Text rendering templates**: English labels (consistent with the rest of the codebase; the underlying data - course names, topics, notes - stays whatever language the user wrote it in, same language-neutral approach as the RAG prompt itself). Assistant drafted, user reviewed twice (once for content, once to make the labels English instead of the first German draft) before implementation - see `src/studylife_ai/ingestion/rendering.py`.
- **API surface verified directly against the StudyLife .NET source** before deciding (not assumed): confirmed exact routes/DTOs/auth for `/api/courses`, `/api/sessions/history`, `/api/coursegoals` via a full read of the relevant controllers - see the actual research findings folded into this decision rather than duplicated here.

### 2026-08-11 — Qdrant schema: `note_id` renamed to `entity_id`, plus `content_type` **[owner: assistant]**
- **Decision**: renamed `NoteChunkMetadata`/`RetrievedChunk`'s `note_id` field to `entity_id` throughout (`qdrant_store.py`, `sync.py`, `rag/prompt.py`, `schemas/chat.py` - `NoteSource` renamed to `Source`), and added a `content_type: Literal["note", "course", "session", "course_goal"]` field. `get_known_fingerprints()` now keys by `(content_type, entity_id)`; `delete_entity()` filters on both fields together.
- **Why the rename, not just adding `content_type` alongside the old name**: every call site touching the field changes regardless (the value stored is no longer always a note, and the fingerprint-dict key type changes either way), so the rename adds no extra diff on top of that - and keeping a field called `note_id` holding a course's id would permanently misname persisted data for anyone reading it later. Filed as refactoring/typing, which CLAUDE.md puts fully in my hands, not a design decision needing sign-off.
- **Why both `content_type` and `entity_id` matter together**: a course and a note can both have numeric id=5 - without `content_type` disambiguating, a course delete could wipe a same-numbered note's chunks. Covered by an explicit regression test (`test_qdrant_store.py`'s `delete_entity` filter-conditions test, `test_sync.py`'s cross-type collision test, `test_prompt.py`'s mixed-type grouping test).
- **Required manual step, not a code path**: the existing dev Qdrant collection had old-schema points (`note_id`, no `content_type`) that would `KeyError` under the new schema. No backward-compat shim written - the collection was dropped and rebuilt from scratch via a full `sync_all()` run instead (cheap: single-user, ~170 points).
- **Self-referencing `course_id`/`session_id`**: for a `course`-type point, `course_id` is `None` (it isn't "about" a course, it *is* one), same for `session_id` on session-type points - simpler semantics than self-referencing, easy to revisit since nothing downstream consumes it yet.

### 2026-08-11 — `sync.py`: one shared helper, one `sync_all()` orchestrator **[owner: assistant]**
- **Decision**: replaced `sync_notes()` with a private `_sync_content_type()` helper (parametrized by plain callables: `entity_id`, `fingerprint`, `render_text`, `title`, `course_id`, `session_id`) capturing the diff/chunk/embed/upsert/delete control flow once, called once per content type from a single public `sync_all(settings)`.
- **Why a shared helper**: the control flow is ~15 real lines with branching (new/changed/deleted, conditional `ensure_collection`), duplicated 4x verbatim except for field extraction - real duplication, not the "three similar lines" CLAUDE.md warns against over-abstracting.
- **Why one orchestrator instead of 4 public `sync_X()` functions**: `get_known_fingerprints()` always scrolls the *entire* collection (no server-side content-type filter) - calling it once per type would scroll the full collection 4x for nothing. The four StudyLife API fetches inside `sync_all()` run concurrently via `asyncio.gather` (found missing in code review - they're independent, no reason to pay each round-trip in series).
- **`CourseGoalDto` has no own `id`** - the API returns at most one goal per course, so `entity_id=lambda g: g.course_id`. Commented at the call site: if that assumption ever breaks (more than one goal per course), this silently keeps only the last-diffed goal, no error.
- **Session lookback is a rolling window, not a fixed historical boundary** (found in code review, comment was initially wrong about this): `days=1825` is measured from "now" on every sync run, so a session eventually ages out and gets deleted from the index exactly like a session that was actually deleted in StudyLife - not distinguishable, and not a one-time fetch boundary. Accepted as-is (5-year-old sessions have little retrieval value for a personal study assistant), but documented accurately in `config.py` instead of the original misleading comment.

### 2026-08-11 — SSE `sources` event shape changed for content-type awareness **[owner: assistant]**
- **Decision**: `schemas/chat.py`'s `NoteSource` (`note_id`, `title`, `course_id`) renamed to `Source` (`content_type`, `entity_id`, `title`, `course_id`) - `content_type` imports `ContentType` from `qdrant_store.py` rather than redefining an equivalent `Literal` (code review finding: two independently-defined literals for the same concept can silently drift apart if a 5th content type is ever added). `rag/prompt.py`'s citation numbering (`[1] Course: ...`, `[2] Session: ...`) now prefixes each block with a content-type label so the model (and a future frontend) can tell entity types apart, not just note titles.
- **Consequence for API consumers**: this is a breaking change to the `/chat` SSE `sources` event's JSON shape. Not a concern yet - no frontend consumes it (that's a separate, later step per CLAUDE.md's architecture table).

### 2026-08-11 — Second code-review round: process finding, real fixes, accepted debt **[owner: user + assistant]**

It *was* shown concretely in the implementation plan the user approved via `ExitPlanMode`, but as one finished proposal, not as alternatives to choose between - a real gap in following the process, even though the outcome (this exact format) was re-confirmed as the preferred one once actual alternatives were offered afterward. **[owner: user]**
- **Fixed** (real correctness/safety issues found in review, all cheap): **[owner: assistant]**
  - `delete_entity`'s `content_type` parameter was typed `str` instead of `ContentType` - the one method that actually deletes data had no static protection against a typo'd content type silently matching nothing and no-op'ing the delete.
  - The session title lambda in `sync.py` duplicated `"%Y-%m-%d %H:%M"` as a literal instead of importing `rendering.DATETIME_FORMAT` - could have silently drifted from the embedded body text's own date format.
  - `_sync_content_type()` now logs a warning if two entities of the same content type resolve to the same `entity_id` (the `CourseGoalDto`-has-no-own-`id` assumption, generalized) - previously a silent overwrite with no signal at all.
  - The four DTOs' identical `ConfigDict(alias_generator=to_camel, populate_by_name=True)` were pulled into a shared `_StudyLifeDto` base class in `models.py`, so a future config tweak can't land on only some of them.
- **Accepted as documented debt, not fixed in this pass** (real inefficiencies, but pre-existing patterns from the original notes-only `sync_notes()` now applied across 4 passes instead of 1 - fixing properly is a bigger refactor than this PR's scope): **[owner: assistant]**

Not addressed here (reranking, per-type minimum quotas, or raising `top_k` are all Retrieval-Design decisions per CLAUDE.md, reserved for the user) - left as retrieval behaves today, to be revisited if/when it's actually a problem in practice.

## M4 — Agent actions (LangGraph, confirmed writes)

### 2026-08-11 — M4 scope: endpoint, tools, confirmation mechanism, checkpointer **[owner: user]**
- **Decision**, made before any implementation (goal explained, then options with trade-offs presented, per standing process):
  - **Integration point**: a new `POST /agent` (+ `POST /agent/confirm`) endpoint, not an extension of `/chat`. `/chat` stays pure RAG with no tool-calling risk; the agent is opt-in surface, not a behavior change to existing traffic.
  - **Tool scope**: "Sessions anlegen" (`create_study_session`) and "Notizen zusammenfassen" (`search_notes` + `save_note`) only. "Timer starten" was dropped after research (see below) found StudyLife has no real server-side timer to start - the actual countdown runs entirely client-side in Blazor; the one related API (`PUT /api/timerstate`) is a passive status mirror with no server-driven effect. An agent tool for it would set a flag that does nothing.
  - **Confirmation mechanism**: a structured propose-then-confirm flow, not conversational ("ja"/"nein" parsed by the LLM). The agent never executes a write directly - `POST /agent` returns a pending action (tool + args + a `thread_id`), and a separate `POST /agent/confirm` call executes or rejects it. Chosen over conversational confirmation specifically because it doesn't rely on an LLM correctly interpreting an ambiguous or adversarial "yes" - a deterministic API call is the actual gate, not a text classification.
  - **Checkpointer**: SQLite-backed (`langgraph-checkpoint-sqlite`'s `AsyncSqliteSaver`), not in-memory. A pending-but-unconfirmed write must survive a service restart between propose and confirm - LangGraph's own docs mark the in-memory saver "debugging/testing only." Verified live: proposed a session, killed and restarted the FastAPI process, confirmed successfully against the same `thread_id` from the new process.
- **Research before deciding, not assumed**: both the StudyLife write-API surface (`POST /api/sessions`/`POST /api/notes` request shapes, that `CourseId` is never validated against the real catalog, the plain-string `400` error bodies, the `TimerStateController` finding above) and LangGraph's current human-in-the-loop API (`interrupt()`/`Command(resume=...)`, and that `create_react_agent` is deprecated in favor of `create_agent` + `HumanInTheLoopMiddleware` from the `langchain` package) were verified directly against the StudyLife .NET source and current LangChain/LangGraph docs before any of this was proposed.

### 2026-08-11 — Implementation choices for the agent stack **[owner: assistant]**
- **`create_agent` (from `langchain`) + `HumanInTheLoopMiddleware`, not `create_react_agent`**: the latter (`langgraph.prebuilt.create_react_agent`) is deprecated in current LangGraph (v1), removal planned for v2. `create_agent` pulls in the full `langchain` package as a dependency, not just `langgraph` - a bigger footprint than "LangGraph" alone implies, but the only current, non-deprecated way to get pause-before-write-tool support without hand-rolling the interrupt node.
- **`langchain-litellm`'s `ChatLiteLLM`, not `langchain_community.chat_models.ChatLiteLLM`** (already used for the M3 eval judge): the community one is a dev-only dependency pulled in for ragas; using it for the agent too would promote `langchain-community` to a runtime dependency just for this. `langchain-litellm` is the officially-listed LiteLLM integration and stays a dedicated, purpose-built package.
- **No per-request `model` override on `AgentRequest`** (unlike `ChatRequest`): the compiled agent graph is built once at startup with one bound model - swapping it per request would mean rebuilding the whole graph, not a cheap parameter. Dropped rather than half-implemented.
- **`QdrantStore.search()`/`retrieve_chunks()` gained an optional `content_type` filter**: needed so the new `search_notes` tool searches only notes, not courses/sessions/goals too. Additive and optional (defaults to `None` = no filter) - doesn't change the existing v1 "no metadata filter" retrieval-design default that `/chat` still uses.
- **Current date/time injected as a `SystemMessage` on every `POST /agent` call**: found live, not anticipated - without it, relative dates ("morgen", "übermorgen") got resolved against the model's training data instead of the real date (a test asking for "morgen" produced a session dated in 2023). Fixed by prepending `SystemMessage(f"The current date and time is {now}.")` before the user's message, computed fresh per request (baking it into a startup-built system prompt would go stale within a day). Local time, not UTC - matches how StudyLife itself stores session timestamps.

### 2026-08-11 — Code review: error handling, multi-action turns, deployment volume **[owner: assistant]**
- **Unhandled tool failure permanently "poisoned" a thread_id** (found in review, reproduced live before fixing): if a write tool raised (e.g. StudyLife rejecting invalid input), the exception propagated as an unhandled 500, and the checkpointed state was left exactly where it was (`state.next` still non-empty) - a client retrying `POST /agent/confirm` with the same `thread_id` would silently retry, and fail, the identical tool call forever, with no way to recover except starting an entirely new conversation. Fixed: both endpoints now catch the failure, delete that thread's checkpoint (`checkpointer.adelete_thread`) so a retry correctly gets a `404` instead of an infinite failure loop, and return `502` with a generic message instead of a raw 500.
- **A turn with two simultaneous write-tool calls crashed on confirm** (found in review, reproduced live): nothing stops the bound model from proposing e.g. `create_study_session` and `save_note` in one turn if it decides to (confirmed reproducible with parallel-tool-calling-capable models). The original code only surfaced the first `action_request` to the client and always sent a single-element decision list on confirm, which `HumanInTheLoopMiddleware` rejects with a `ValueError` (decision count must match interrupted-call count) - another unhandled 500. Fixed: `AgentResponse.pending_actions` is now a list (was a single optional field), and `POST /agent/confirm` reads the real pending count from `aget_state()` before resuming and applies its one decision to all of them. Explicit simplification, not a full fix: there's no way to approve one action and reject another in the same turn - documented in the schema, revisit if it's ever actually needed.
- **`docker-compose.yml` had no volume for the SQLite checkpoint file** (found in review): the whole point of choosing SQLite over in-memory was surviving a restart, but without a volume the file lived in the `app` container's writable layer and would be lost on every `docker compose up --build` anyway - silently defeating that decision in the one environment meant to demonstrate it. Fixed: `agent_data` named volume mounted at `/app/data`, `AGENT_CHECKPOINT_DB_PATH` overridden to point there for the containerized deployment.

## Retrieval quality: reranking + per-content-type quota

Picks up the "Retrieval-Design question, not a bug" flagged at the end of the ingestion-scope-expansion section above: `RETRIEVAL_TOP_K=5` shared across 4 content types produced a noisy top-5 (measured baseline: Context Precision 0.58) and could push a genuinely relevant chunk out of the running entirely once a popular course's many near-duplicate `session` chunks outnumbered it.

### 2026-08-11 — Approach: two-stage retrieval, LLM-as-reranker, independent `RERANK_MODEL` **[owner: user]**
- **Decision**, resolving the three retrieval-quality sub-questions (goal explained, options with trade-offs presented, per standing process):
  - **Approach**: two-stage retrieval - fetch a wider candidate pool by vector search, rerank, keep the best `RETRIEVAL_TOP_K`. Industry-standard shape (cheap recall-oriented first stage, more expensive precision-oriented second stage).
  - **Rerank method**: LLM-as-reranker (prompt an LLM to reorder candidates), not a dedicated rerank API. `litellm.arerank()` was checked live and only supports Cohere/Voyage/Together/DeepInfra/Fireworks/watsonx - none work with Ollama, so a dedicated rerank provider was rejected specifically to keep "runs with zero API keys" true for local dev.
  - **Model**: a new, independent `RERANK_MODEL` setting (unset by default = no reranking, today's behavior unchanged), not reusing `LLM_MODEL` - lets a small/fast model be picked for this simple scoring task independent of the answer model.
- **Implementation** [owner: assistant]: `rag/rerank.py`'s `rerank_chunks()` builds a plain-text prompt (not JSON mode, for small-local-model compatibility) listing each candidate as `[i] {title}: {content, truncated to 300 chars}`, asks for indices most-to-least relevant as a comma-separated list. Parsing keeps only valid in-range indices, dedupes, appends any indices the model omitted at the end, and falls back to the unchanged original order on any parse failure or LLM exception - a bad rerank result degrades retrieval, never breaks it.

### 2026-08-11 — Investigation: mixed initial results traced to Ollama embedding instability, not reranking **[owner: assistant]**
- **What happened**: the first reranking-only eval run showed Context Precision improving (0.58→0.83) but Answer Relevancy and one note-match case (`tutor-frage`) regressing. Investigated rather than accepted at face value: confirmed the Qdrant point count was unchanged (167) between runs, confirmed embeddings were deterministic *within* a session (two identical calls, same vector), then found the specific `tutor-frage` regression predated reranking entirely - present even in plain, non-reranked top-5 - pointing at cross-session embedding non-determinism from the local Ollama embedding model rather than a reranking bug.
- **Decision** [owner: user]: permanently switched `EMBEDDING_MODEL` from `ollama/nomic-embed-text` to `openai/text-embedding-3-small` (new Qdrant collection, full re-ingestion - embedding-model changes aren't a config flip, the vector space itself changes). Fixed `tutor-frage`, but surfaced a second, different finding below.

### 2026-08-11 — Second finding: a true recall gap, beyond any reranking candidate window **[owner: assistant]**
- **What happened**: with OpenAI embeddings, a different case (`lgs-loesen`) still missed. Traced the expected note's rank among *all* note candidates: position 28 - far beyond `rerank_candidate_k=20`, meaning it never became a rerank candidate in the first place. Reranking (a precision fix - reordering a given candidate pool) structurally cannot fix a recall problem (whether the relevant chunk is even in that pool).
- **Decision** [owner: user]: add a per-content-type minimum candidate quota, used *together with* reranking, not instead of it - confirmed explicitly ("reranking in Verbindung mit Mindestkontingent pro Kategorie"). `retrieve_with_rerank()` (`rag/retrieval.py`) now fetches an even quota from each of the 4 content types separately (`rerank_candidate_k` split evenly, e.g. 5 each at the default 20) and merges them, instead of one global top-`rerank_candidate_k` vector search - a type with many entities (sessions) can no longer squeeze a type with few (notes) out of the pool purely by outnumbering it. Always active (independent of whether `rerank_model` is set), since it's a recall fix, not a reranking-specific one. Reranking is then applied on top of the merged pool when configured.
- **Live-verified**: `lgs-loesen`'s expected note (`Lineare Gleichungssysteme lösen`) now returns as the top source; the earlier course-crowding case (a course's own chunk narrowly losing to session duplicates) also confirmed fixed.

### 2026-08-11 — Third finding: reranker was blind to `content_type`; partial fix chosen over a hard quota **[owner: user]**
- **What happened**: even with both fixes, one eval case (`statistik-breit`, a broad "what did I note about statistics" question expecting *two* different notes) still missed - not a recall problem (both expected notes were confirmed present in the note-type candidate pool, ranks 1 and 4 of 5), but the LLM reranker deprioritized both of them below 4 session chunks + 1 course chunk in the final merged ranking.
- **Root cause**: the rerank prompt showed only `{title}: {content preview}` per candidate - the LLM had no way to know a candidate's `content_type`, so it couldn't weigh a strong signal like "notiert" (noted/wrote down) toward the `note` type specifically.
- **Options presented**: (1) add `content_type` as a visible label in the rerank prompt - minimal, non-prescriptive, lets the LLM use the signal without forcing an outcome; (2) additionally add a hard post-rerank floor (force the top note candidate into the final result if zero notes survive reranking) - stronger, but risks injecting an irrelevant note into questions where genuinely none is relevant (e.g. the `cloud-kein-treffer` test case, which exists specifically to verify no-note-found is handled honestly).
- **Decision**: chose (1) only. `_build_prompt()` now renders `[i] ({content_type}) {title}: ...`. Verified this measurably helped (a note now survives into the final top-5 for `statistik-breit`, where none did before) without fully solving it (the *specific* expected notes still don't both make the cut) - a real, structural trade-off between 4 content types and 5 final slots for the same topic, not a bug.
- **Dedicated reranker API considered and rejected for this specific problem**: a cross-encoder reranker (Cohere Rerank, BGE-reranker, etc. - the more typical production-RAG choice, pointwise-scored rather than the listwise LLM-prompt approach used here) would likely rank relevance more accurately in general, but wouldn't reliably fix `statistik-breit` specifically - the issue there is 4 content types competing for a fixed number of final slots on the same topic, a structural quota problem independent of ranking-function quality. Not pursued given no clear payoff for this concrete gap, plus the same Ollama-incompatibility trade-off already rejected for the same reason in the original approach decision above.
- **Accepted as a known, documented limitation** [owner: user]: the harder post-rerank quota floor (option 2 above) remains a valid follow-up if this class of multi-note broad question turns out to matter more in practice - not built now.

### 2026-08-11 — Final measured results **[owner: assistant]**
- **Baseline** (pure vector search, no reranking, shared top-5 across content types, Ollama embeddings): Faithfulness 0.77, Answer Relevancy 0.90, Context Precision 0.58, note-match 92% (11/12 - `statistik-breit` was already the one miss even then).
- **Final** (per-content-type quota + LLM reranking with `content_type` labels + OpenAI embeddings, `RERANK_MODEL=openai/gpt-4o-mini`): Faithfulness 0.82, Answer Relevancy 0.82, Context Precision 0.92, note-match 92% (11/12 - `statistik-breit` still the one miss, for the different, now-understood reason above).
- **Net**: Context Precision improved substantially (0.58→0.92) - the metric this whole investigation set out to fix. Faithfulness improved slightly (0.77→0.82). Answer Relevancy dropped somewhat (0.90→0.82) - not separately investigated, candidate explanation is the embedding-model switch changing which passages are considered "relevant" by the judge's own relevance model; flagged here rather than assumed, revisit if it doesn't hold up under future eval runs. Note-match rate unchanged at 92%, but for a materially different reason than the baseline (a structural multi-note quota gap now, not the course-crowding/recall-window gaps this round fixed).

## M4.5 — Multi-user support

Inserted between M4 and M5, not folded into either. Triggered by a concrete question before starting M5 ("is the current state multi-user capable like StudyLife itself?"): no - `studylife-ai` has no auth on its own endpoints, builds exactly one `StudyLifeClient` from one `.env`-configured key at startup, and nothing enforces `user_id` filtering at retrieval today (see the original "Single-user scope for now" decision, M2). Confirmed real future need (family members), so this becomes its own milestone rather than a documented-but-deferred capability - retrofitting after M5 ships a single-user-shaped deployment would be more disruptive than designing it in now. All five sub-decisions below made via the standing goal-then-options process **[owner: user]**.

### 2026-08-11 — Auth flow: StudyLife backend proxies the request
- **Goal**: a request from the Blazor chat component to `studylife-ai` must be provably (not just claimed) tied to a real, logged-in StudyLife user.
- **Decision**: Blazor WASM calls a new endpoint on StudyLife's own ASP.NET Core backend (e.g. `POST /api/ai/chat`), not `studylife-ai` directly - reversing the architecture diagram's current `BlazorUI -- chat --> FastAPI` direct edge. StudyLife's backend already knows the caller (existing passkey session), holds that user's `AiApiKey` server-side, and forwards the request to `studylife-ai` with it attached.
- **Alternative considered**: Blazor WASM calls `studylife-ai` directly, fetching its own `AiApiKey` once from StudyLife at chat-widget load. Simpler (no new StudyLife-backend endpoint, matches the already-drawn architecture diagram), but puts a long-lived, powerful credential into browser-held state for the session's duration - inspectable via DevTools, a real difference from how this key has only ever been used server-side (originally built for "non-interactive integrations" per the StudyLife source comments).
- **Why**: the key never leaving StudyLife's own server is worth the extra cross-repo endpoint and the architecture-diagram change.

### 2026-08-11 — Identity signal: forward the user's own `AiApiKey`, not a separate assertion
- **Decision**: StudyLife's backend forwards the logged-in user's actual `AiApiKey` with the proxied request. `studylife-ai` uses it directly to build a per-request `StudyLifeClient` (no separate identity-resolution call) - the key simultaneously proves legitimacy and serves as the credential for downstream StudyLife API calls (`list_courses`, `create_session`, etc.).
- **Alternative considered**: a fixed server-to-server shared secret (proves "this is really StudyLife's backend calling") plus a separately-asserted `user_id` field. Cleaner separation of "is this legitimate" from "which user", but `studylife-ai` would still need each user's `AiApiKey` for downstream calls, meaning a second lookup mechanism to fetch it - more moving parts for no real gain given the key is already available to the trusted proxy.
- **Consequence**: `main.py`'s `_lifespan` no longer builds one `StudyLifeClient` at startup - client construction moves to per-request, keyed by the incoming `AiApiKey`.

### 2026-08-11 — Qdrant partition key: the real StudyLife-internal user id, not a hash of the key
- **Decision**: StudyLife's backend sends the resolved internal user id alongside the `AiApiKey` (it already has both, synchronously, no extra round-trip) - `studylife-ai` uses that id as the Qdrant `user_id` payload value.
- **Alternative considered**: hash of the `AiApiKey` itself, avoiding a second field. Rejected: rotating an `AiApiKey` (e.g. after a suspected leak - precisely the scenario rotation exists for) would change the hash and orphan that user's entire Qdrant index, forcing a full re-ingestion just to recover from a routine security action.

### 2026-08-11 — Ingestion: a static, manually-maintained user list, not a privileged "list all users" endpoint
- **Decision**: the ingestion worker (a separate process, run manually/cron - not triggered by a live request) gets a small config-driven list of `(user_id, ai_api_key)` pairs in `studylife-ai`'s own settings, one per family member, manually updated when someone new joins.
- **Alternative considered**: a new privileged StudyLife endpoint (e.g. `GET /api/admin/ai-users`) returning every configured user's key, enabling real self-service (ingestion discovers new users automatically). Rejected: true self-service isn't needed at family scale, and an endpoint that exposes every user's credential in one response is a meaningfully larger attack target than any single user's own key - one compromise instead of needing several.

### 2026-08-11 — Agent checkpoint ownership: user id embedded in `thread_id`, not a separate ownership table
- **Decision**: `thread_id` is generated as `f"{user_id}:{uuid4()}"`. `POST /agent/confirm` checks the caller's own resolved `user_id` against the `thread_id` prefix and rejects with `403` on mismatch *before* touching the checkpointer at all - no foreign pending-action state is ever read, let alone resumed.
- **Alternative considered**: a separate `thread_id -> user_id` ownership table, checked on every confirm. Cleaner in the abstract (`thread_id` carries no user info), but adds a new schema/migration/write-path solely for this one check, with no other use for the table - unjustified for this project's scale given the prefix approach needs no new persistence at all.

### Still open, not yet designed
- Exact implementation across both repos (StudyLife `.NET` backend proxy endpoint; `studylife-ai`'s per-request client construction, ingestion loop rewrite, mandatory `user_id` enforcement at every retrieval call, `thread_id` scoping in `agent/graph.py`/`api/agent.py`).
- Whether `RETRIEVAL_TOP_K`/`RERANK_CANDIDATE_K` and other settings stay global or become per-user-tunable (leaning global for now - no evidence yet that different family members need different retrieval tuning).
