# Demo walkthrough

Real examples from live testing against production, not scripted or invented — every question/answer pair below is verbatim. Where a fix has a "before" and "after", the "before" is the actual broken output that motivated the fix, not a hypothetical.

## 1. RAG: answering from your own notes and calendar, with citations

`POST /chat` — "welche session haben wir heute?" (11.08.2026):

> Heute, am 11. August 2026, sind mehrere Studien-Sessions im Kurs "Künstliche Intelligenz" geplant. Die Sessions sind wie folgt:
>
> 1. Von 16:00 bis 17:30 Uhr, Thema: Wissensrepräsentation [1].
> 2. Von 18:00 bis 19:30 Uhr, Thema: Wissensrepräsentation [3].
> 3. Von 20:00 bis 21:30 Uhr, Thema: Wissensrepräsentation [2].
>
> Du hast also insgesamt drei Sessions heute!

The `[n]` citations map to a deterministic `sources` list in the same SSE stream (content type, entity id, title, course id) — the caller never has to trust the model got the citation right, since the source list is built from what was actually retrieved, not generated by the LLM (see [Prompt design](decisions.md#m2--ingestion-architecture-planning-ahead-of-implementation)).

## 2. Agent: proposing a write action, never executing it directly

`POST /agent` — "Leg mir für morgen 16:00 bis 17:30 Uhr eine Lernsession für 'Neuronale Netzwerke und Deep Lerning' an, Thema Backpropagation." (deliberately misspelled course name):

```json
{
  "answer": null,
  "pending_actions": [{
    "tool": "create_study_session",
    "args": {
      "course_id": 13,
      "course_name": "Neuronale Netze und Deep Learning",
      "start_time": "2026-08-12T16:00:00",
      "end_time": "2026-08-12T17:30:00",
      "topic": "Backpropagation",
      "notes": null
    },
    "thread_id": "5:96c5462e-3278-4832-abc2-4842f2bb22dc"
  }]
}
```

The agent resolved the misspelled name to the real course via `list_courses` before proposing anything — nothing executes until `POST /agent/confirm` with that `thread_id` and an explicit `approve`.

## 3. Agent: asking instead of guessing when a name is genuinely ambiguous

Same mechanism, a harder case — live-tested directly against production with two real, similarly-named courses ("Studium Generale I" / "Studium Generale II"):

"Leg mir für nächsten Montag 14:00 bis 15:30 Uhr eine Lernsession für 'Studium Generale' an."

> Es gibt zwei Kurse, die mit "Studium Generale" verwandt sind:
>
> 1. **Studium Generale I** (SG-601)
> 2. **Studium Generale II** (SG-602)
>
> Welchen dieser beiden Kurse meinst du?

No `pending_actions` — the agent didn't invent an answer to a question it didn't have enough information to answer. This didn't happen by default: see the case study below for what changed and why.

## 4. Case study: getting date-relative questions actually right

This is the most instructive thread from the session, because none of the individual fixes worked on the first attempt — each one was tested live, found insufficient or wrong, and replaced or supplemented by the next. Full detail with all the intermediate live evidence: [docs/decisions.md, "Post-M5 production hardening"](decisions.md#post-m5-production-hardening).

**The starting bug.** "welche Session ist für morgen geplant?" answered "keine Sessions geplant", even though a session existed for that date. Root cause: pure vector-similarity search has no notion of "close to today" — a text embedding can't rank by date, so the correct session simply never survived the initial top-k cut.

**Attempt 1 — teach the reranker about dates.** Added a `today` date to the reranker prompt and an instruction that a session far from the asked-about date isn't relevant. Fixed "today" and "tomorrow". Broke on "übermorgen" (day after tomorrow): the prompt's examples only covered a few English phrasings, and the model conflated "close to today" with "matches the question" — a session from 3 days *before* today satisfied "übermorgen" just because it was nearby in time, not because it was the right direction or offset.

**Attempt 2 — generalize the instruction.** Reworded the prompt to resolve exact offsets for any relative phrase, in any language. Fixed "übermorgen". Broke on "vorgestern" (day before yesterday) with a **worse** failure mode than before: the model fabricated a session with an invented time range instead of citing the wrong one.

**Root cause, precisely.** Sessions had no structured date field in Qdrant — only free text. The reranker was being asked to do real date arithmetic while scanning dozens of near-identical "Course, YYYY-MM-DD HH:MM" passages, purely from reading. Two more prompt-wording rounds weren't going to fix a capability problem with wording.

**Attempt 3 — a real structural fix.** Sessions gained an actual `session_start` field in Qdrant, `DATETIME`-indexed, filtered with a genuine range query instead of asking an LLM to read dates out of text. Verified directly against real Qdrant (not mocked) before deploying: a narrow single-day window returned exactly the right session for both "morgen" and "übermorgen" offsets. Deployed — "vorgestern" *still* failed, and the identical query sometimes returned different answers to the identical question.

**Attempt 4 — determinism.** The reranker's LLM call had no `temperature` set. Pinned it to `0.0`. Fixed some of the inconsistency, not all of it.

**Finding the actual ceiling.** Reproduced the exact failing call directly against production (`kubectl exec` into the live pod, real query, real 41-session candidate pool, real prompt). The pool was correct. Passage `[6]` was labeled, correctly and unambiguously, `[2 days ago]` — exactly what "vorgestern" needed. The model's raw response:

```
RAW RESPONSE: '0'
```

A single index, choosing a passage labeled `[6 days ago]`, and truncating its answer instead of ranking all 41 candidates as instructed. Not a prompt problem anymore — `gpt-4o-mini` couldn't reliably follow the instruction at this candidate-pool size, even with the correct answer labeled in plain sight.

**Attempt 5 — the actual fix.** Upgraded the reranker to `gpt-4o`. Tested live in production *before* committing to it — a temporary `kubectl set env` override with Flux's GitOps reconciliation paused, no code pushed — to confirm it was a real fix and not a fluke:

| Question | Result |
|---|---|
| heute | ✅ |
| gestern | ✅ |
| vorgestern | ✅ |
| **vorvorgestern** (day before day-before-yesterday — not even in the prompt's example list) | ✅ |
| morgen | ✅ |
| übermorgen | ✅ |

Only after that live confirmation was it committed to the ConfigMap and the GitOps pause lifted.

**What this thread demonstrates**, beyond the specific bug: the difference between a plausible-sounding fix and a verified one. Every attempt above looked reasonable when written; three of the five were wrong or incomplete in ways only live testing against real data surfaced. The final fix layers four independent things, each targeting a different part of the failure that the layer above it couldn't reach: structured data (fixes *recall*), deterministic labels (removes arithmetic from the model's job), pinned temperature (removes run-to-run variance), and a capable-enough model (the actual bottleneck once the other three stopped being confounds).
